# ROLE

Act as a senior Node.js automation engineer and responsible B2B outreach
strategist. Build "ClientVelo Engine": a lightweight, CLI-only Node.js MVP for
low-volume, high-quality local-business prospecting and outreach (10-20 emails
per day at most). No frontend.

Priorities, in order: safety and correctness, terms-compliant data collection,
human review before any outreach, conservative deliverability practices,
crash-safe resumable state, and simplicity. This is a 7-day experiment, so
prefer a small, reliable, testable tool over feature count.

# EXECUTION RULES

1. Before writing any code, produce an implementation plan: architecture, file
   tree, data schemas, CLI commands, config variables, safety controls, testing
   plan, risks and assumptions. Then STOP and wait for my approval.
2. Build in the four phases below. After each phase: run tests and a dry-run
   demonstration, show the output, summarize what was done, then STOP for approval.
3. Never send a real email unless ALL of these are true: DRY_RUN=false, the
   --send flag is present, the draft is approved (hash matches), the message
   passes validation, the recipient is not suppressed, it is not a duplicate,
   the effective daily cap is not reached, the send window is active, and the
   operator confirmed the batch (when confirmation is enabled).
4. Never invent facts. Every claim in an email must trace to a measured audit
   value or a source URL.
5. Keep the project to roughly 20 source files. Merge small modules. No stub
   or placeholder modules.

# DATA-COLLECTION RESTRICTIONS

Do NOT implement: Google Maps scraping or bulk export, CAPTCHA bypass, login
bypass, proxy rotation, stealth or fingerprint-spoofing browsers, anti-bot
evasion, access to anything behind technical controls, automatic contact-form
submission, or guessing email addresses from patterns (info@, firstname@, etc.).

The default lead source is a CSV I prepare by hand. Put sourcing behind a small
provider interface so a permitted API can be added later.

Playwright is used only for bounded inspection of public business websites
listed in my CSV:
- max 4 pages per domain (homepage, contact, about, one service page)
- per-page timeout, per-domain delay, max response size
- respect robots.txt where applicable
- clean failure handling; skip and log unreachable sites
- never crawl a whole domain or submit forms

# STACK

Node.js 20+, TypeScript run with tsx, ESM. Dependencies: playwright,
nodemailer, dotenv, zod, tsx. Tests use node:test, run with:
  node --import tsx --test tests/*.test.ts
CLI scripts use: tsx src/cli.ts <command>. A minimal console logger is fine;

# LEAD DATA MODEL

Base: id, businessName, category, city, country, websiteUrl, phone, source,
sourceUrl, sourceCheckedAt, rating, reviewCount, contactName (optional),
createdAt, updatedAt.

Contact: contactChannel (direct_email | generic_email | contact_form |
phone_only | none | needs_manual_review), emailCandidates[] (all found emails,
each classified), email (chosen), emailType (business_public | generic_role |
personal_public | unknown), chosenEmailReason, requiresManualAction.

Validation: emailValidationStatus (not_checked | syntax_valid | domain_has_mx |
role_address | invalid | needs_manual_review).

Audit: auditStatus (not_checked | complete | partial | failed | site_unreachable),
psiStatus (unavailable | complete | disabled), screenshotPath, and an `audit`
object with: viewportMeta, horizontalOverflow, telLink, bookingKeywordFound,
bookingCtaAboveFold, whatsappOrSocialBookingLink, loadTimeMs, psiMobileScore
(nullable), httpStatuses. Plus: primaryIssue, evidenceUrl, evidenceText,
personalizationNote.

Primary issues: slow_or_heavy_mobile_page, no_visible_booking_cta,
no_click_to_call, contact_path_has_friction, site_unreachable,
no_material_issue_detected.

Scoring: qualificationScore, qualificationReasons[].

Workflow status: new, enriched, validated, needs_review, approved, drafted,
sent, replied, bounced, opted_out, skipped.

Store no unnecessary personal data.

# CSV IMPORT

Columns: businessName,category,city,country,websiteUrl,phone,rating,
reviewCount,contactName,source,sourceUrl

Command: import --file <path>. Validate required fields, normalize URLs, remove
exact duplicates, preserve source metadata, write invalid rows to an error
report (never silently drop), safe to re-run, protect against path traversal.

# ENRICHMENT

Extract only publicly visible info: mailto links, visible business emails,
simple obfuscations ("name [at] domain.com", "name (at) domain (dot) com"),
phone numbers, contact-form presence, page title, service descriptions.
Preserve all email candidates, classify each, pick a preferred one with a
written reason. If only a contact form exists: contactChannel=contact_form,
email=null, requiresManualAction=true.

# AUDIT

Playwright at 390x844. Measure only observable values (the audit fields above)
and save one screenshot per lead. Thresholds live in config (LOAD_SLOW_MS,
PSI_POOR_SCORE, above-the-fold definition). Before flagging
no_visible_booking_cta, also check for WhatsApp, Messenger, and social booking
links, and treat those as a booking path. PSI is optional (AUDIT_PSI_ENABLED);
if PSI is unavailable the audit still completes with psiStatus=unavailable.
Never claim a site is losing customers or revenue; use cautious wording such as
"may make it harder for mobile visitors to...".

# EMAIL VALIDATION

Syntax check, domain normalization, MX lookup via dns.promises.resolveMx with
timeout, optional disposable-domain check, role/blocked classification.
- Role addresses (info@, contact@, hello@, office@, support@, sales@, admin@)
  are flagged and ranked lower, not rejected.
- Blocked (noreply@, no-reply@, abuse@, postmaster@, mailer-daemon@) are excluded.
- MX success only means the domain advertises mail servers. It does not prove
  the mailbox exists or that delivery will succeed. No SMTP mailbox probing.
  Never claim zero bounces or call an address "verified" on MX alone.
Output: data/leads_validated.json.

# QUALIFICATION

Score only from observable evidence: niche match, city match, has website,
audit completed, clear issue, minimum reviewCount (config), contactability,
evidence quality. Output qualificationReasons. Only leads I mark approved may
enter drafting.

# DRAFTS

Plain text only. Body = greeting + exactly 3 sentences + footer.
- Greeting: "Hi {contactName}," if present, else "Hi there,".
- Sentence 1: a specific measured observation (with the real value).
- Sentence 2: cautious possible consequence for mobile visitors.
- Sentence 3: a tiny yes/no CTA, e.g. "Would you like me to send a 60-second
  video showing one possible fix?"
- Footer (outside the 3 sentences): sender name, business name, postal address,
  opt-out line.
- 2-3 variants keyed by primaryIssue (slow page, no booking CTA, no click-to-call,
  unclear contact path).
- Subject: accurate, natural, under 8 words, not deceptive; the business name is
  optional.
- Never: guaranteed-loss or revenue claims, fake familiarity, fake urgency,
  "Re:"/"Fwd:" prefixes, attachments, links, images, tracking pixels, or the word
  "redesign".
- Rendering FAILS on any missing/undefined/null token, missing compliance field,
  or banned phrase ("losing customers", "you are losing", "guaranteed",
  "revenue", ...).
- drafts.json entries start with approved:false and support an optional
  customOpener.
- `approve` command binds approval to a hash of recipient + subject + body. Any
  edit voids approval and the send queue must re-verify the hash.

# SUPPRESSION

data/suppression.json records {email, reason, createdAt, source}. Commands:
mark-opt-out, mark-bounce, mark-invalid (all suppress immediately) and
mark-replied (sets status=replied, does NOT suppress). Suppression is checked
immediately before every send, even for previously approved drafts.

# SEND QUEUE

Nodemailer over configurable SMTP (Gmail App Password allowed for testing; any
provider via env). One message at a time.
- Pre-send re-checks: DRY_RUN, --send, approval hash, syntax/MX status,
  suppression, duplicate status, daily count from dispatch_logs.json, send
  window/days, effective cap, sender identity, postal address, opt-out line,
  valid subject/body.
- Effective cap = min(DAILY_SEND_LIMIT, RAMP_SCHEDULE value for the current
  campaign day), computed from the log, never memory.
- Random delay between MIN_DELAY_SECONDS and MAX_DELAY_SECONDS. Delay is pacing
  only, not a deliverability guarantee.
- Retry only transient SMTP errors (MAX_RETRIES); never retry permanent
  recipient errors. Stop the run after 2 consecutive SMTP errors.
- Bounce stop: halt sending if 2 or more marked bounces occur within the last 20
  sends, or if bounces/sent exceeds BOUNCE_STOP_RATE once 50+ have been sent.
  (Bounces arrive later as messages, so mark-bounce feeds this rule.)
- Duplicate prevention: exact recipient + campaignId + message hash + existing
  dispatch records. Optional DOMAIN_COOLDOWN_DAYS (adjustable, not absolute).
- Graceful Ctrl+C, crash-safe state updates.
- Before a live batch, print a preview (recipient, business, subject, daily
  count X/Y, window status, dry-run flag) and require confirmation when
  SEND_CONFIRMATION_REQUIRED=true.
- Log every attempt to dispatch_logs.json: leadId, recipient, businessName,
  campaignId, messageHash, timestamp, status (dry_run | sent | transient_error |
  permanent_error | suppressed | duplicate | skipped), messageId, smtpResponse,
  errorCode, retryCount, dryRun.
